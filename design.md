# SvirisTel (svt_)

Платформонезависимая p2p реализация протокола канального уровня.

Изначально SvirisTel ориентирован на работу поверх UART, но не привязан к нему и потенциально может применяться поверх любого протокола физического уровня. Однако SvirisTel не реализует символьную (байтовую) синхронизацию (старт/стоп биты), и это стоит учитывать, в случае непредусмотренного применения.

## Технологический стек

- Чистый C99, без внешних зависимостей.
- Фрейминг COBS (Consistent Overhead Byte Stuffing).
- Контрольная сумма CRC-16/IBM-SDLC, табличная реализация.

## Глоссарий

- Кадр - последовательность данных закодированная в кадр COBS.
- Чанк - часть данных в кадре COBS не содержащая нулей (между кодами COBS).
- Сегмент - часть обрабатываемых данных условного или произвольного размера.
- Payload (SDU) - необрабатываемые пользовательские данные верхнего уровня.
- PDU - незакодированная COBS структура данных включающая служебные поля протокла и SDU.
- uplink - обработка и передача данных в сеть.
- downlink - получение и обработка дданных из сети.
- Пользователь - разработчик использующий данную реализацию SvirisTel.
- Пользовательский контекст - код написанный разработчиком в котором применяется API SvirisTel.
- Микробатчинг - обработка передаваемых или получаемых данных небольшими порциями.

## Структуры передаваемых данных

### PDU

```
+-----+--------+---------+--------+
| PID | Length | Payload | CRC-16 |
+-----+--------+---------+--------+
```

| Поле | Размер | Описание |
|------|--------|----------|
| PID | 1B | Protocol ID. |
| Length | 2B | Длина полезной нагрузки, BigEndian. `MTU = 4092` (4095 − 1 PID − 2 Length). Поле 16-битное, максимум ограничен маской `0xFFF` для точности CRC-16. |
| Payload | (Length)B | Полезная нагрузка (SDU). |
| CRC | 2B | CRC-16/IBM-SDLC, BigEndian. |

CRC-16/IBM-SDLC: полином `0x1021`, init `0xFFFF`, refin=false, refout=true, xorout `0xFFFF`.
Вычисляется над `PID + Length + Payload` в порядке следования байт на проводе (BigEndian).

### Кадр COBS

```
+-----+-----+---------+-----+---------+-----+     +-----+---------+-----+
| DOF | OHB | Chunk 1 | OHB | Chunk 2 | OHB | ... | OHB | Chunk N | DOF |
+-----+-----+---------+-----+---------+-----+     +-----+---------+-----+
```

| Поле | Размер | Описание |
|------|--------|----------|
| OHB (Overhead Byte) | 1B | Указатель на следующий за чанком непередаваемый 0x00. |
| DOF (Delimiter Of Frame) | 1B | Разделитель кадров = 0x00. |
| Chunk | 0..254B | Последовательность от 0 до 254 произвольных байт не содержащая нулей. |

Кадр COBS обрамляется двумя DOF: один в начале, один в конце.

Внутри кадра нули не передаются. PDU разбивается на чанки, и перед каждым чанком
ставится OHB, значение которого равно `длина чанка + 1` — то есть указывает на позицию
следующего нуля (или DOF) относительно самого OHB. При декодировании OHB заменяется
нулём, а байты чанка копируются как есть.

Последний OHB кадра указывает на завершающий DOF.

OHB — один байт, поэтому его значение не превышает `0xFF` (255), а длина чанка — 254 байта.

Особый случай: если OHB = `0xFF`, чанк заполнен целиком (254 байта) и нуля в нём нет.
Тогда следующий за чанком байт — это не ноль, а очередной OHB; при декодировании он
не превращается в `0x00`, а просто отбрасывается.

## Архитектура

### Объектно ориентированный подход реализации

Реализация SvirisTel определяет структуру контекста которая передается в каждую функцию API для выполнения операции в контексте конкретного экземпляра SvirisTel.

Структура контекста хранит уникальные для экземпляра SvirisTel таблицу колбэков, параметры и состояние, что позволяет обслуживать несколько независимых линков/портов.

### Политика использования памяти

SvirisTel не имеет собственных буферов, вместо этого используются пользовательские буферы. Поэтому, пользовательский контекст должен сам управлять выделением памяти под буферы отправки и приема данных.

SvirisTel гарантированно изменяет (кодирует или декодирует) данные в предоставленных буферах. Поэтому, если пользователю необходимо сохранять исходные данные, он должен выполнять их копирование в независимый буфер перед вызовом функций обработки данных SvirisTel.

### Потоковая обработка данных

Потоковая обработка данных реализована с использованием микробатчинга для снижения частоты вызова функций передачи и обработки данных.

**Микробатчинг uplink операций** выполняется в контексте SvirisTel, но ограничивается пользовательским контекстом. При каждом его вызове, выполняется строго одна uplink операция в следующей последовательности:
```
1.    Start - 
        вычисляется CRC, 
        формируются служебные сегменты Header = DOF + coded{ PID + Length } и Trailer = coded{ CRC-16 } + DOF,
        фреймер COBS кодирует весь PDU, 
        выполняется передача Header в пользовательский контекст для отправки в сеть.
2.    Run - выполняется передача закодированного Payload в пользовательский контекст для отправки в сеть.
3.    Run - так как пользовательский контекст не смог отправить весь закодированый Payload, отправляется оставшаяся часть.
...
n.    Run - выполняется передача остатка закодированного Payload в пользовательский контекст для отправки в сеть.
n+1.  Completion - выполняется передача Trailer в пользовательский контекст для отправки в сеть.
```
Минимальное возможное количество операций = 3.
SvirisTel при операциях uplink передает в пользовательский контекст указатель и полный размер уже закодированных Header, Payload или Trailer, а пользовательский контекст сам ограничивает размер передаваемых за раз данных.

**Микробатчинг downlink операций** выполняется в пользовательском контексте. SvirisTel способен получать и обрабатывать сегмент данных произвольного размера синхронно за единственный вызов. В рамках одного вызова выполняется:
1. декодирование кадра COBS.
2. парсинг PDU.
3. передача значений PID и Length в пользовательский контекст (единожды при получении).
4. передача SDU в пользовательский контекст (при каждом получении).

### Разделение уровней обработки данных

1. **Фреймер COBS** - кодирует кэш Header, Trailer и Payload при uplink, либо декодирует принимаемые сегменты при downlink.
2. **Сереализатор PDU** - разбирает PID, LENGTH, PAYLOAD, CRC из принятого потока декодированных байт или складывает незакодированные PID, LENGTH, CRC в кэш Header, Trailer.
3. **Валидатор** - вычисляет и сравнивает CRC, сравнивает Length с фактическим размером принятого кадра.

## API

### Функции

| Функция | Описание |
|---------|----------|
| `svt_init` | Инициализация контекста: регистрация таблицы колбэков и пользовательского контекста, сброс машин состояний. |
| `svt_reset` | Принудительный сброс машин состояний и Tx-кэша (аварийная ресинхронизация). |
| `svt_send` | Зарегистрировать передачу: сохранить указатель на буфер SDU и число байт. Буфер остаётся валидным до `on_tx_end`. |
| `svt_poll` | Продвинуть TX (запускает `tx_worker`). |
| `svt_push` | Подать произвольный массив сырых данных из UART в потоковый декодер RX. Разбор и вызовы `on_rx_*` выполняются синхронно внутри вызова; возвращает `SVT_OK`. |

### Колбэки

| Колбэк | Описание |
|--------|----------|
| `on_tx_write` | Вывод порции закодированного COBS-потока в физический интерфейс (DMA/FIFO). |
| `on_tx_end` | Завершение передачи с кодом результата (позволяет освободить буфер). |
| `on_rx_start` | Уведомление о начале приёма кадра, передаётся PID. |
| `on_rx_data` | Передача декодированного куска полезной нагрузки в код пользователя. |
| `on_rx_end` | Завершение приёма с итогом валидности кадра (фрейминг + CRC). |

### Структуры данных

| Структура | Назначение |
|-----------|------------|
| `svt_ctx` | Контекст протокола: колбэки, Tx-кэш батчинга, состояния TX/RX, пользовательский контекст. |
| `svt_callbacks` | Таблица методов-колбэков. |
| `svt_tx_cache` | Кэш батчинга TX: накопление закодированных COBS-байт перед `on_tx_write`. |

### Коды возврата

| Код | Значение |
|-----|----------|
| `SVT_OK` | Успех. |
| `SVT_BUSY` | Канал занят передачей предыдущего кадра (`svt_send` до `on_tx_end`). |
| `SVT_ERR_ARG` | Некорректный аргумент (нулевой указатель, нулевая длина). |
