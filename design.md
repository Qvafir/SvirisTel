# Дизайн SvirisTel (svt)

Платформонезависимая реализация p2p протокола канального уровня.

Изначально SvirisTel ориентирован на работу поверх UART, но не привязан к нему и потенциально может применяться поверх любого протокола физического уровня. Однако SvirisTel не реализует символьную (байтовую) синхронизацию (старт/стоп биты), и это стоит учитывать, в случае непредусмотренного применения.

## Технологический стек

- Чистый C99, без внешних зависимостей.
- Фрейминг COBS (Consistent Overhead Byte Stuffing).
- Контрольная сумма CRC-16/IBM-SDLC, табличная реализация.

## Глоссарий

- Кадр - последовательность данных закодированная в кадр COBS.
- Чанк - часть данных в кадре COBS не содержащая нулей (между кодами COBS).
- Сегмент - часть обрабатываемых данных условного или произвольного размера.
- SDU - необрабатываемые пользовательские данные верхнего уровня.
- PDU - незакодированная COBS структура данных включающая служебные поля протокла и SDU.
- uplink - обработка и передача данных в сеть.
- downlink - получение и обработка дданных из сети.
- Пользователь - разработчик использующий данную реализацию SvirisTel.
- Пользовательский контекст - код написанный разработчиком в котором применяется API SvirisTel.
- Микробатчинг - обработка передаваемых или получаемых данных небольшими порциями.
- Кодирование - формирование передаваемого кадра в соответствии с протоколом COBS.

## Структуры передаваемых данных

### PDU

```
+-----+-----+-----+--------+
| PID | SDL | SDU | CRC-16 |
+-----+-----+-----+--------+
```

| Поле    | Размер    | Описание                                                                                                                                           |
| ------- | --------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| PID     | 1B        | Protocol ID.                                                                                                                                       |
| SDL  | 2B        | Длина полезной нагрузки, BigEndian. `MTU = 4092` (4095 − 1 PID − 2 SDL). Поле 16-битное, максимум ограничен маской `0xFFF` для точности CRC-16. |
| SDU | (SDL)B | Полезная нагрузка (SDU).                                                                                                                           |
| CRC     | 2B        | CRC-16/IBM-SDLC, BigEndian.                                                                                                                        |

CRC-16/IBM-SDLC: полином `0x1021`, init `0xFFFF`, refin=false, refout=true, xorout `0xFFFF`.
Вычисляется над `PID + SDL + SDU` в порядке следования байт на проводе (BigEndian).

### Кадр COBS

```
+-----+---------+-----+---------+-----+     +-----+---------+-----+
| OHB | Chunk 1 | OHB | Chunk 2 | OHB | ... | OHB | Chunk N | FDL |
+-----+---------+-----+---------+-----+     +-----+---------+-----+
```

| Поле                  | Размер  | Описание                                                              |
| --------------------- | ------- | --------------------------------------------------------------------- |
| OHB (Overhead Byte)   | 1B      | Указатель на следующий за чанком непередаваемый 0x00.                 |
| FDL (Frame Delimiter) | 1B      | Разделитель кадров = 0x00.                                            |
| Chunk                 | 0..254B | Последовательность от 0 до 254 произвольных байт не содержащая нулей. |

Внутри кадра нули не передаются. PDU разбивается на чанки, и перед каждым чанком
ставится OHB, значение которого равно `длина чанка + 1` — то есть указывает на позицию
следующего нуля (или FDL) относительно самого OHB. При декодировании OHB заменяется
нулём, а байты чанка копируются как есть.

Последний OHB кадра указывает на FDL.

OHB — один байт, поэтому его значение не превышает `0xFF` (255), а длина чанка — 254 байта.

Особый случай: если OHB = `0xFF`, чанк заполнен целиком (254 байта) и нуля в нём нет.
Тогда следующий за чанком байт — это не ноль, а очередной OHB; при декодировании он
не превращается в `0x00`, а просто отбрасывается.

## Архитектура

### Объектно ориентированный подход реализации

Реализация SvirisTel определяет структуру контекста которая передается в каждую функцию API для выполнения операции в контексте конкретного экземпляра SvirisTel.

Структура контекста хранит уникальные для экземпляра SvirisTel таблицу колбэков, параметры и состояние, что позволяет обслуживать несколько независимых линков/портов.

### Политика использования памяти

SvirisTel не имеет больших внутренних буферов, заисключением небольшого tx буфера фиксированного размера, настраиваемого пользователем. 
Пользовательский контекст обязан сам управлять выделением памяти под буферы отправки и приема данных, а также заниматься их записью и освобождением при полученни колбэков SvirisTel. 

Это сделано с целью сохранить гибкость управления памятью, и предоставить пользователю возможность независимо использовать любые реализации буферов.

Буфер микробатчинга необходим по причине наличия потенциоального оверхеда фреймера COBS, который добавляет 1 дополнительный байт данных на каждые подряд идущие 254 байта ненулевых данных.

### Потоковая обработка данных

Потоковая обработка данных реализована с использованием микробатчинга для снижения частоты вызова функций передачи и обработки данных. 
Основная идея микробатчинга, это работа функций API с сегментами данных вместо обработки каждого отдельного байта.

**Микробатчинг Tx потока** выполняется автоматически, а объем батчинга фиксирован и устанавливается размером внутреннего tx буфера.

Вызов функций отправки данных и опроса состояния включает основные операции:
1. вычисление CRC (единожды, при первом вызове).
3. кодирование сегмента PDU.
4. передача сегмента в пользовательский контекст для передачи в сеть.


**Микробатчинг Rx потока** выполняется за счет деления принимаемых данных на сегменты с произвольным размером. 

SvirisTel получает и обрабатывает сегмент данных произвольного размера за единственный вызов (синхронно). Поэтому пользовательский контекст может разбивать поток получаемых из сети данных на сегменты и передавать их в SvirisTel, контролируя, таким образом, объем батчинга. 

Если в сегменте будет несколько кадров (конец певрого и начало второго), то будет обработана только часть сегмента до начала второго кадра, часть сегмента со вторым кадром останется нетронута до следующего вызова. Это делается воизбежание множественных повторных внутренних вызовов, для обеспечения детерминированности времени работы необходимой для асинхронности.

В рамках одного вызова функции получения данных выполняется:
1. декодирование полученного сегмента или полного кадра COBS.
2. частичный или полный парсинг PDU и вычисление CRC.
3. передача значений PID и SDL в пользовательский контекст (единожды при получении).
4. передача SDU в пользовательский контекст (при каждом получении сегмента или единожды при полном SDU).
